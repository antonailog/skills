## 严重（2）

### S1 对比表「来源」列从 URL 到编号的转换没人做，`render_table.py` 一定报错
- **位置**：research-guide.md:90（「来源」列填 URL）；writing-guide.md:132（报告员跑 render_table）；scripts/render_table.py:8、45-48（只认数字编号）；scripts/build_source_table.py:128（只 glob 顶层 `*.md`，不读 `40-dossier/*.csv`）
- **问题**：研究员按指南在 CSV 里填 URL，`render_table.py` 遇到非数字就报「来源不是编号」并退出 1（实测）。`build_source_table.py` 也不扫 CSV，只在 CSV 里出现过的 URL 拿不到编号。旧版这一步由「验证者」把 URL 换成编号（旧 dossier-fields.md:8），删掉验证者后没人接这一步。
- **为什么会出事**：多对象对比表是「对比报告」的主要载体。报告员要么贴不出表，要么手工逐个查号；查不到号（URL 根本不在 sources.json），就只能删表，或者编一个号。研究员照 research-guide.md:90 自检时同样会撞上这个报错，可能为了让脚本通过去乱填编号。
- **建议**：让 `build_source_table.py` 同时扫 `40-dossier/*.csv` 的「来源」列，并把 CSV 里的 URL 原地替换成编号（或另写一份编号版 CSV）；`render_table.py` 也可以改成接受 URL、按 sources.json 查号。research-guide.md:90 那句「render_table 能检查空格子」改成只查空格子的用法，或者删掉。

### S2 没定工作目录的根；落点那一步会把多份报告的 `charts/`、`research_notes/` 混在一起
- **位置**：SKILL.md:52、SKILL.md:88、红线 3（SKILL.md:105）
- **问题**：
  1. 「报告与 `charts/` 放在它的上一级」。「它」字面上指 `research_notes/<课题>/`，上一级就是 `research_notes/`；可别处（SKILL.md:10、writing-guide.md:91 的 `charts/guide.svg` 相对路径、`--out-dir charts`）都假定报告、`charts/`、`research_notes/` 三者同级。根目录在哪也没写，默认就是会话 cwd，通常是工作区根，而工作区根是 git 仓库。
  2. 第 6 步默认把 md 放进「`知识/调研/` 下最贴的现有子目录」，再把 `charts/`、`research_notes/` 一起移过去。同一个子目录放第二份报告时，两份报告的 `charts/guide.svg`、同名图会互相覆盖，`research_notes/` 也会合并。红线 3 只保护 md，不保护这些目录。现有实践（`知识/调研/Jev-2026-10-11/`、`AI陪伴型产品赛道-2026-10-10/`）是一份报告一个目录。
- **为什么会出事**：覆盖掉的是上一份已交付报告的图，覆盖不可恢复。两个课题并行时，也会在 cwd 下共用一个 `charts/`。
- **建议**：开工时建 `<草稿根>/<对象>-<日期>/`，报告、`charts/`、`research_notes/` 都放在里面，所有命令的相对路径都以它为准。落点改成「把整个 `<对象>-<日期>/` 目录移到 `知识/调研/<子目录>/` 下」，目录重名时加序号。红线 3 相应改成「不覆盖已有的报告目录」。

## 中（9）

### M1 `check_report.py` 有四类误报，报告员会为了「修到零错误」改坏正常写法
- **位置**：check_report.py:116-123（尾部顺序）、:56 与 :180-182（角色标签）、:281（结论章定位）、:305-308（W17）
- **问题**（前三类实测复现）：
  1. **E3 误报**：判断「口径与来源」位置时，脚本取第一个含「来源」的二级标题；章标题里一出现「来源」（如「三、钱：收入来源集中在 API」），就报「尾部顺序应为……」。报错文字指不到真正的原因。
  2. **E5 误报**：「对你」等词在「一分钟看懂」整节里做子串匹配，结论格写「对你的抽取项目值得先试一周」也报错。指南（writing-guide.md:96）禁的是拿它当**行名**，结论格本来就该「落到读者具体的项目」。另外脚本还拦「给你的建议」，指南没提这一项。
  3. **W12 找错章**：取第一个章名里含「结论 / 要不要 / 值不值 / 选型」的章。前面某章的判断句里有「结论」二字（如「二、输入输出：官方结论是……」），就会拿那一章的第一张表去查「通过 / 放弃、周期、预算」列。
  4. **W17**：标题没有《》「」、不超过 14 字、空格分词不超过 2 段就判为可疑，「Jev 官方博客发布说明」这类正常的中文短标题都会被报。
- **为什么会出事**：writing-guide.md:196 要求错误修到 0、警告逐条改。报告员会去改好好的章名、结论和来源标题来迁就脚本。
- **建议**：尾部定位与 :136 一样，取最后一个「来源」标题，或者只认以「口径与来源」开头的标题；角色标签只查事实表第一列；结论章按 `00-plan.md` 大纲里的模块名（结论 / 集成判断）定位；W17 去掉「≤2 段且 ≤14 字」这一条，或者只对纯域名 / 纯站名生效。

### M2 第 1 步要协调者「从写作指南的模块库补」章节，但协调者的阅读清单里没有写作指南
- **位置**：SKILL.md:45（协调者只读本文件和框架文件）、:57、:96-98（按需读取表写的是写作指南只给报告员和审读员读）；frameworks/*.md:7
- **问题**：模块名决定 `00-plan.md` 的大纲，`check_report.py` 又按大纲核对章名，所以协调者必须知道有哪些模块、每个模块放什么。按现在的清单，他不会去读 writing-guide.md 第 3 节。
- **为什么会出事**：协调者会自造模块名，报告员在模块库里找不到对应写法。补「输入输出章」这类关键章时，协调者也不知道这一章该要求研究员查哪些东西。
- **建议**：第 1 步第 2 条点名「读 writing-guide.md 第 3 节的章节模块库」，按需读取表里加一行「协调者，第 1 步：第 3 节」。或者把模块库挪进 frameworks/generic.md，让协调者只读框架文件。

### M3 「够不够」和停止条件太松，第 ② 个目标「把每章材料找齐」没有可检查的抓手
- **位置**：research-guide.md:13 与 :104（停止条件）、:81-86（「够不够」格式）；SKILL.md:67、:71
- **问题**：标准要的是广度：「每个问题、每个关键角度都有材料，机制要找到一手说明」。停止条件却是「每个问题都有带链接的材料」，一个问题有一条链接就算满足。「够不够」只写一句结论加缺口，由研究员自评，不需要逐项对照任务书里抄进去的「要查什么」。协调者只读这一节，看不出缺了哪个角度，比如输入输出章缺官方原样的请求和返回示例。旧版 `coverage_report.py` 删掉之后，没有东西接替它。
- **为什么会出事**：研究员自评「够」，协调者就不会补研。缺的东西到了报告员那里才暴露，而报告员「不做新研究」，只能写薄。
- **建议**：「够不够」改成一张表，每行对应任务书里的一个「要查什么」条目，写明有几条材料、有没有一手来源、缺什么、试过哪些渠道。停止条件第一条改成「每个『要查什么』条目都有材料，机制条目有一手说明」。协调者按表里的「缺」和「0 条」来判断要不要补研。

### M4 「要有输入输出章」的触发条件比它背后的教训窄
- **位置**：SKILL.md:22（Jev 的教训：用户问「是什么、怎么实现、有什么用」，输入输出被挤成一个小节）、SKILL.md:57（只写了「问到用法、接口就要有输入输出章」）、frameworks/ai-tool.md:7（「用不上的章删掉」）
- **问题**：Jev 那次用户的原话里没有「用法」「接口」这些词。照第 1 步的规则，「有什么用」不会触发输入输出章，ai-tool 框架默认的输入输出章也可能被当成「用不上」删掉。这正是用户抱怨过的问题。
- **建议**：对 ai-tool 类型（模型、API、CLI、skill、MCP），把输入输出章写成不可删，不再按用户措辞去判断；其他类型再按「问到怎么用 / 接入 / 吃什么吐什么」来判断。research-guide 的笔记格式也要允许贴原样的代码块（官方请求和返回示例）。现在「每条发现一个事实」的格式容不下代码块，报告员就拿不到「官方原样示例」。

### M5 审读员的范围有两个版本，第 5 条实际是证据审查
- **位置**：SKILL.md:81（只看 4 件事：问题有没有回答、一分钟看懂、外行读不读得懂、图）；writing-guide.md:204-212（7 条）
- **问题**：两处范围不一致。第 5 条「说得太满：……倍数没有依据、单一来源被写成定论」，要判断这一条就得知道哪些说法只有一个来源，而审读员只读报告和 `00-plan.md`。要么他判断不了，要么他自己去翻笔记，变成证据审查。这和「不做证据审查、审读员只看可读性」的既定方向冲突。
- **建议**：先定一个版本。如果保留第 5 条，就改成只看措辞：全称词、最高级、没有给出数字的倍数，不去判断来源够不够。SKILL.md:81 改成「按第 11 节逐条看」，不要在这里另列一份清单。

### M6 「每个小节：加粗结论句 + 2—4 条证据要点，不写成一段论证」和「机制讲透」「像老手讲课」打架
- **位置**：writing-guide.md:104；对照 SKILL.md:12、:24，writing-guide.md:121（「跟着推理走：有条件、有转折 → 文字」）、:157（洞见要写推理）
- **问题**：机制章（怎么实现、钱怎么流）要讲清因果链，靠的是连贯的短段落。一律写成「结论句 + 要点」会把报告切成 PPT 式的碎片，读者拿到一堆结论，却看不到「为什么」。再加上 W7（连续 600 字没有表或列表就告警），压力全推向列表。
- **建议**：分两种小节来写：讲事实的小节用「结论句 + 证据要点」；讲机制和推理的小节用「结论句 + 2—4 个短段落」，每段 ≤3 句，按因果顺序写，配一张结构图。

### M7 「还不知道的」没有筛选标准，容易变成新的「留给你的问题」
- **位置**：writing-guide.md:49-52（表头：问题 / 试过的渠道 / 怎么补）、:187（「够不够」里的缺口全部进这一章）
- **问题**：所有没查到的东西都会被倒进这一章，表头里也没有一列说明这个缺口影响什么。用户已经因为「留给你的问题没用」把那一节砍掉了，换成这个格式可能还是没用。
- **建议**：只收会影响读者决定或某条判断的缺口。加一列「影响哪条判断 / 决定」；对决定没有影响的缺口，合并成一行写进「口径与来源」。审读清单相应加一条：这一章每一行都说明了它影响什么吗？

### M8 第 6 步要传 `--theme <主题>`，但没有人把报告员选的主题交回来
- **位置**：SKILL.md:85；writing-guide.md:200（报告员回复的是路径、图几张、表几张、检查脚本最后一行）；make_chart.py:12、:673（没给主题就报错）
- **问题**：协调者不知道该传哪个主题。随便选一个，重画出的数据图就和导引图、Mermaid 图的风格不一致；不重画，重编号之后图上的来源编号就是错的。
- **建议**：报告员把主题名写进 `00-plan.md`（或者在每个图表 JSON 里写 `"theme"` 字段），并在回复里带上；第 6 步从那里读取。

### M9 本机代码没有引用格式，和「没有原文链接不进报告」冲突
- **位置**：frameworks/ai-tool.md:17（集成判断章的来源是读者本机代码，路径由协调者列出）；research-guide.md:40（「没有链接的数字，报告员不能用」）；SKILL.md:103 红线 1；build_source_table.py 只认 http(s) 链接
- **问题**：AI 工具报告里，读者真正要做的决定落在集成判断章，而这一章的事实来自本机文件，没有 URL。照现在的规则，研究员不知道怎么记，报告员不能用，来源表也不给它编号。旧 Jev 报告里是自创了「本机：路径:行号」的写法。
- **建议**：在研究指南的取数顺序里加上「本机文件」，统一记成 `本机：<相对路径>:<行号>`；红线 1 写明本机来源用路径代替链接；写作指南第 9 节说明本机来源在「口径与来源」里怎么列（不编号，或者单独编一组号）。

## 轻（18）

### L1 脚本路径、检查命令前后不一致
SKILL.md:64、:73、:85 写的是 `python3 scripts/xxx.py research_notes/<课题>`：`scripts/` 相对的是 skill 目录，`research_notes/` 相对的是工作目录，两者不可能同时成立。如果为了跑脚本 cd 到 skill 目录，`research_notes/` 就会建在 skill 包里。其他地方写的都是 `<skill 目录>/scripts/`。SKILL.md:77 的检查命令只有 `--plan 00-plan.md`（相对路径，也缺 `--sources`），和 writing-guide.md:196 的完整命令对不上。**建议**：统一写成 `python3 <skill 目录>/scripts/...`，SKILL.md:77 直接写「按写作指南第 10 节第 6 步跑检查」。

### L2 笔记文件名有歧义，第二轮补研会覆盖第一轮
- 一个研究员负责两章时，SKILL.md:65 写的是 `10-<章>.md`（单数），research-guide.md:61 写的是「每章一节，写到任务书指定的路径」。到底是一个文件放两节，还是两个文件，没有说清；`<章>` 用章号还是模块名也没定。
- SKILL.md:72 说最多补两轮，但两轮都写 `11-<章>.md`，第二轮会覆盖第一轮。writing-guide.md:187 只列了 `10-*`、`11-*`。
- **建议**：一章一个文件，命名 `10-<章号>-<模块名>.md`；第 n 轮补研写 `1n-<章号>-<模块名>.md`；写作指南改成读 `1*-*.md`。

### L3 几类状态标注没有传给报告员
SKILL.md:60 的「计划未经用户确认」、:111 的「单线程」、:114 的「自有信息流没用上」、:113 的「知乎没用接口」，都要求写进报告。但第 4 步的任务书没有带上这些状态，writing-guide.md:41 的导读行模板也没有留位置。**建议**：在 `00-plan.md` 里加一节 `## 运行状态`，报告员照着写进导读行和「口径与来源」。

### L4 分层阅读表里的固定用时，和「篇幅不设目标」不一致
writing-guide.md:13-17 写「10 分钟」「30 分钟」，读起来像篇幅目标；而 :11 写「篇幅不设目标」，:41 的导读行又用 `<N>`、`<M>` 按实际估算。**建议**：表里的用时改成「约 X 分钟（按全文字数估）」，或者删掉这一列。

### L5（存疑）60 次上限和「不设搜索预算」
SKILL.md:67 和 research-guide.md:106 都写了累计 60 次，research-guide.md:102 又写「满足任一条就落盘」，这实际上就是预算。一个研究员负责两章、还要兼顾广度和一手机制说明时，60 次搜索加抓取未必够。如果只是为了防失控，建议改成「超过 N 次先回报协调者」，而不是到了就停。

### L6 脚本里残留旧版术语和机制
- build_source_table.py:2「evidence family」、:215「验证者按内容确认是否转引同源」、:220「弱来源……报告里不能单独撑结论」：验证者这个角色已经没有了，协调者收到这些输出也不知道该怎么处理。
- own_feed_recall.py:7、:99「从信息需求清单拆」：02-needs 是旧术语，现在应该是「从计划拆」；:186「核查以 JSON 里的原文为准」。
- fetch_article.py:17「研究员规程」，应为「研究指南」。
- zhihu_search.py:17「每次运行算 2 次搜索预算」。
- render_table.py:9「未查到（试过：X、Y）」，而 research-guide.md:90 写的是「未查到」。

**建议**：措辞统一到新版；build_source_table 的 family 提示和弱来源提示可以删掉，或者改成写给报告员看的「同源多篇只算一个来源」。

### L7（存疑）`30-judgments.md` 的「反面材料」一行，是旧「反例名单」的残留
writing-guide.md:30、:32 要求每个判断都列反面材料，并且要在正文出现。如果它的用途是让结论写清边界（这属于写作），可以保留，但要说明 why，并且说清没有反面材料时怎么处理。如果它是旧对抗审查留下来的，就删掉，以免报告员按旧习惯去做证据审查。

### L8（存疑）结论表强制要「周期」「预算」两列，对公司类、人物类、事件类不适用
writing-guide.md:169 和 check_report W12 对所有类型都要求这两列。像「要不要入职」「这个政策对我意味着什么」这类决定，硬加一列「预算」只会填出空话。**建议**：这三列只对 product、industry、ai-tool 三类要求，其他类型改成「先验证什么 + 放弃信号」。

### L9 导引图的模块数有下限，指南没写
make_guide.py:71 要求 4—12 个模块（docstring :17 写的却是 6—10）。用户只问 1 个问题时，大纲是「是什么 / X / 还不知道的」3 章，导引图生成不出来。**建议**：writing-guide.md:99 注明「少于 4 章时不画导引图，用读法导航行代替」，或者让脚本放宽下限；同时把 docstring 和代码改成一致。

### L10 generic.md 里写了维护 skill 的指令
frameworks/generic.md:24-26 让执行者「整理成新的框架文件，并在 SKILL.md 的按需读取表里加一行」。执行者可能在跑调研的过程中去改 skill 本身，而且按需读取表本来就是用 `<类型>` 通配的。**建议**：删掉，或者挪到仓库层面的维护说明里。

### L11 计划确认这一步缺「先展示」，也没有按既定方向确认分工
SKILL.md:60 用一次 AskUserQuestion 确认「问题、读者与决定、大纲」，但没要求先把确认单和大纲贴出来（或给出 `00-plan.md` 的链接），而多选题里放不下一份 8 章的大纲。既定方向是「确认单、大纲、分工一次确认」，现在漏了分工（存疑：如果作者有意不让用户看分工，就把背景里那条改掉）。**建议**：先在回复里贴出确认单、大纲和事实行，再问「按此开工 / 我要改」。

### L12 图表用了正文没引用过的来源，重编号后图上的编号会指错
renumber_sources.py:180、:212：图表 JSON 里正文没引用过的编号会原样保留，重编号之后它就指向另一个来源，脚本只打印一句「注意」。writing-guide.md:129 没要求「图用到的来源编号必须在正文里也出现」，SKILL.md:85 也没说遇到这句「注意」该怎么处理。**建议**：写作指南补上这条要求；第 6 步看到「注意」就退回报告员处理。

### L13 推荐阅读：编号检查实际不起作用，公众号来源和「必须可点」冲突
check_report.py:275 的条件是「没有编号**并且**没有 http」才告警，而 E9 已经要求每条都有 http 链接，所以 writing-guide.md:177 要求的 `[n]` 永远不会被查出来。公众号来源的链接外人打不开（writing-guide.md:176），放进推荐阅读也点不开。**建议**：W10 改成单独检查 `[n]`；写作指南写明公众号来源不进推荐阅读。

### L14 「一分钟看懂」和正文的数字是否一致，没有人检查
writing-guide.md:97 要求「事实表的每一格都要能在正文找到带编号的出处」，但脚本不查，审读清单也不查。检查前后是否一致属于可读性，不算证据审查。前后数字打架是常见的坏报告形态。**建议**：审读清单第 2 条加一句：事实表的每一格，能不能在正文找到同一个数？

### L15 「每个关键数字配参照」没有研究侧的输入
writing-guide.md:150 要求报告员给数字配上对手、同比、上一代这类参照，但研究指南没要求研究员收集参照数据，报告员又「不做新研究」。**建议**：research-guide.md 第 3 节加一条：关键数字顺手记下一个参照值（对手的同类数字或上一期数字）。

### L16 来源质量这条信息链是断的
build_source_table.py:37 靠笔记里的「仅见搜索摘要 / 未读原文」标记来识别只读到摘要的来源，但研究指南从来没让研究员写这类标记，所以 writing-guide.md:178 要求的「只读到摘要的在行尾标出」永远不会触发。SKILL.md:89 要把好用和踩坑的来源写回信源库，可协调者没读过笔记，笔记里也没有专门记踩坑的地方。**建议**：research-guide 第 5 节的口径枚举里加上「仅见搜索摘要」，并在「够不够」里加一行「踩坑渠道」，协调者从这里取材料写回信源库。

### L17 多对象材料该放哪儿，规则不全
writing-guide.md:54 说多对象总结表放附录，:68 又说放格局章，两处都写了。:187 说「新发现的对象」进格局章的第二梯队表，可大纲里没有格局章时怎么办，没有交代。**建议**：二选一定死总表的位置；没有格局章时，新发现的对象放进「是什么」章末尾，或者放附录。

### L18 skill-build 写法上的小问题
- description（SKILL.md:3）的触发说法只有「调研一下 / 深度调研 / 全面调研 / 调研报告 / 对比报告」，「竞品分析」「行业研究」「研究一下 X」「摸底一下 X 公司」同样是明确要调研，却没有覆盖到。这和「只在明确要调研时触发」并不矛盾。
- 红线 2、3（SKILL.md:104-105）没有写 why，红线 1、4 都写了。
