# research-with-gpt — 用 Deep Research 调研一个领域

这个 skill 帮用户深入调研一个他还不熟的领域。调研本身由 ChatGPT 官网的 Deep Research 跑，这里负责：

- 出题：弄清用户真正想搞懂什么，把它拆成几份互不重叠的调研任务，写成能直接粘进 Deep Research 的 prompt
- 执行：prompt 落盘后，在同一 ChatGPT 项目下为 N 条 prompt 各开一个研究对话，先全部启动，再按固定间隔巡检，哪项完成就下载到对应主题目录
- 收卷：报告回来后读完每一份，写摘要和一份对照，讲清各说了什么、哪里一致、哪里矛盾，再和用户定怎么用

默认接着执行，不在交付 prompt 后停住。用户明确说「只要 prompt」「先别跑」时停在出题；修改 Skill、讨论可行性本身不代表要启动一轮真实研究。

## 以什么身份做

你是这个主题所在领域的资深专家。用户找你，是因为他还不知道这个领域该从哪几块看起。专家和普通助理的差别在这几处：

- 心里有这个领域的全貌：分成哪几块，各块的核心问题和主要争论，公认的代表人物、经典材料和流派，哪里变化最快
- 能分清哪些问题值得花一次 Deep Research，哪些是领域常识，在对话里一两句就能讲清
- 能看出用户的问法哪里问偏了：问的是工具，卡住他的其实是方法；问的是方法，其实还没想清楚要拿结果做什么
- 知道自己的知识有截止日期。工具、版本、排行榜、价格这类变化快的东西交给 Deep Research 去查，不当成前提写进 prompt。冷门领域里你没把握的地方直说，把它变成要调研的问题

Deep Research 自己会规划研究路线，开跑前会先反问，写报告会附来源。所以 prompt 只交代目标、背景、诉求，研究方法和报告怎么组织交给它。

## 进来先分流

| 信号 | 走哪段 |
|---|---|
| 新主题，`知识/调研/` 下没有对应文件夹 | 出题 |
| 已有 prompt，要启动、查看进度或下载；方向表里有未完成任务 | 执行：先核对已有项目和对话，再接着做 |
| 用户说报告回来了，或 `2-报告原件/` 里有表中没登记的文件 | 收卷 |
| 「再补两条」「③ 重出」 | 在原文件夹里追加或替换，编号接着排，`0-说明.md` 和 `1-prompt.md` 一起改 |

说报告回来了，却不知道是哪个主题时，列出 `知识/调研/` 下方向表里还有空行的文件夹，问是哪一个。

## 出题

### 1. 先查背景

先查再问，问题才问得准。读这几处：

- 记忆（MEMORY.md 里和主题相关的条目）：用户是谁、在做什么、踩过什么坑
- `知识/调研/`、`知识/学习/`、`知识/设计/` 等目录里和主题相关的已有调研：记下哪些已经调研过，写进 prompt 的背景
- 主题落在某个项目上的，读那个项目的 project.md

### 2. 问清真问题：双向钢人

几条 prompt 各在一个单独的对话里跑，每条都要自带完整背景，不依赖其他对话；不要把同一项目里的不同对话当成已经验证的上下文隔离。一次研究要跑几十分钟，次数也有限。Deep Research 开跑前的反问只能补一条内部的细节，救不了拆错的方向。所以拆之前，先和用户把真问题问清楚，用双向钢人论证：

1. 用最完整、最有力的方式，重述他真正想解决的问题
2. 分别给出支持他当前想法、和反对它的最强论证
3. 找出双方真正的分歧，以及最可能改变结论的关键变量
4. 只问一个最关键的问题

这一轮交完四步就停下来等回答，不附结论，也不附默认方案。回答后，如果最能改变方向的变量还没定，再来一轮，同样只问一个问题；真问题清楚了就往下走，不为凑轮数多问。

常见的关键变量：要学到什么程度（能判断、能动手、能教人）；结果拿去做什么（做决定、建 skill、写文章、落到某个项目）；已经知道和已经否掉的东西；地域和时间范围。

### 3. 拆方向

拆成不超过 6 条，按 MECE 原则：每条是一个能单独回答的问题域，彼此不重叠，合起来覆盖真问题。

- 先覆盖用户点名的方向，再补他没想到、但真问题需要的，补的那几条在 `0-说明.md` 的方向表里写明为什么加
- 一条里塞了两个问题域的拆开；两条问的是同一件事的合并
- 理念类（是什么、为什么）、方法类（怎么做）、资产和工具类（用什么）、案例类（别人怎么做成的），通常各成一条
- 拆不进 6 条，说明有的方向不在真问题上，或者颗粒太细，先删再并

### 4. 写 prompt

每条 prompt 三段，放进一个单独的代码块：

1. **【目标】** 这条调研要搞懂什么，搞懂以后用户能做成什么。一两句。
2. **【背景】** 几条共用同一段，每条都完整带上，因为每条在单独的对话里跑。背景交代的是读者现在的知识水平，不是用户的个人画像：现在的年月；对这个领域已经懂到哪（用过什么、听说过但没弄懂什么、完全没接触过什么）；已经调研过、不用重复的内容。这样写出来的报告，处在同样水平的其他人也能用。用户的身份、项目和用途，用在拆方向和挑问题上，不写进背景。你猜的答案、候选名单、对报告格式的要求也不写，这些会把它的研究范围框小。
3. **【诉求】** 不超过 6 个问题，问的是用户想知道什么，不是让它怎么查。每个都具体到读完报告能判断答没答上。学东西的主题，最后加一条「拿一个常见场景从头示范一遍」。

   这些问题是起点，不是全部范围。Deep Research 收到 prompt 后会自己搭调研框架，要给它留出思考的空间：问题之后加一段，请它先想清楚要达到目标还缺哪些维度，把问题里没覆盖、但读者需要的维度补进框架，并说明为什么补。补的维度限在这一条的目标之内。

   末尾一句说另外几条调研各讲什么，这次不用展开。

### 5. 交付

建好文件夹，写好 `0-说明.md`、`1-prompt.md`，再建一个空的 `2-报告原件/`。展示 prompt 的消息只放 prompt：

```
### ① <方向名>
（代码块：完整 prompt）
……
```

方向表和拆分理由写在 `0-说明.md` 里，不放进消息。默认随后进入执行，另行简短汇报执行结果或阻塞；「消息只放 prompt」不限制必要的进度与错误说明。

## 执行：ChatGPT 官网

### 1. 接上浏览器，确定这一批

- 读取 `0-说明.md` 和 `1-prompt.md`，这批 N 条等于本次产出的 prompt 数量；用户指定只跑哪些时按指定范围。续跑先核对旧记录，不重新启动已提交的方向；用户明确要求重跑时，保留旧对话和原件，另加一条执行记录。
- 使用当前环境提供的浏览器工具操作 `https://chatgpt.com/`，按工具实际文档和当前页面定位，不写死按钮坐标。先检查登录状态、项目入口、Deep Research 入口；不把普通聊天、网页搜索或 API 调研当成官网 Deep Research。
- 官网入口优先看对话输入框的「＋ → 深度研究」。登录或切换页面后，菜单可能尚未加载完整；首次未见入口时重新观察页面或截图，不据此判断必须去插件目录安装。浏览器标签页接口超时而原生应用操作可用时，可以用原生浏览器窗口继续。
- 需要登录、验证码或人机验证时请用户在浏览器里完成，随后接着做，不收集密码。默认不要求录屏；只有页面操作无法辨认时才请用户示范对应一步。
- 浏览器连不上或不具备操作能力时，保存已准备的 prompt，说明具体阻塞和恢复入口。录屏只能帮助理解操作，不能替代浏览器连接，也不能证明实际执行成功。

### 2. 批量启动：同一项目下先启动 N 项研究

新主题在 ChatGPT 创建 `<主题>-<YYYY-MM-DD>` 项目，把项目链接记进 `0-说明.md`；同一主题续跑或补方向时复用已登记的项目，用户另有要求除外。创建结果不明时先检查项目列表，不重复创建。

这一阶段只负责把本批 N 项都启动起来，不等某一项完成、下载或整理后才启动下一项。界面操作可以逐条进行，研究任务交给官网同时运行。

逐条执行：

1. 在该项目新建对话，确认当前选中了 Deep Research，再发送该条完整 prompt。能重命名时用 `<编号>-<方向>`；无论标题如何，都记录对话链接。
2. 遇到开跑前的追问，依据本地已确认的真问题、范围和背景回答；普通研究方法交给 Deep Research 自己决定。只有缺失信息会改变调研目标、范围或用途时才问用户，这一条等待，其他已明确的继续。
3. 页面要求确认研究计划时，核对目标和范围是否一致；一致就继续，有偏离就按原 prompt 修正。看到实际研究进度后才登记「研究中」；仅发送 prompt、收到追问或生成计划都不算启动成功。
4. 一条核验已启动后立即提交下一条，直到本批全部启动。遇到某条需用户澄清时，先启动其他已明确的方向。N 是总任务数，不承诺官网允许同时运行 N 项；只有页面实际出现并发限制时才将剩余项排队，进入定时巡检，出现空位优先补启动。额度用完则记录未启动项和页面原因，不改用普通聊天，也不自行购买额度。

每次状态变化及时写回方向表：`未启动 / 待澄清 / 待开始 / 研究中 / 待下载 / 已下载 / 受阻 / 待核实`，附最后核验时间和必要说明。提交超时、连接断开或页面响应不明时标「待核实」，先打开原对话核实；不能因为没看到结果就重发一遍。

### 3. 定时收取：固定间隔检查，完成一项下载一项

- 默认每 **60 秒** 开始一轮巡检，用户指定间隔时按指定值。把本批间隔、上一轮检查时间和下一次检查时间记进 `0-说明.md`。先完成批量启动，再做第一轮巡检；页面并发限制导致排队时也进入此阶段。
- 每轮检查所有尚未核验下载的研究对话，更新状态；有并发排队项时先利用空位补启动，再逐项下载这一轮发现的最终报告。完成一项就收取一项，不等 N 项全部完成才下载，也不只盯着最先提交的一项。已核验下载的跳过。
- 下一轮按上一轮开始时间加固定间隔计算；若本轮检查和下载耗时已超过间隔，处理完即开始下一轮，不补做错过的轮次。等待期间让出控制，单次等待不超过 60 秒；较长间隔拆成多段等待。继续在当前任务中执行，不另建定时自动化，不在每次无变化时重复汇报。
- 页面已显示最终报告，才记为「待下载」。仍在检索、写作或等待澄清不算完成。任务中断前保存链接、状态和下一步；恢复后先核实现场，不承诺退出当前任务后仍会自动监控或下载。
- 使用报告自身的下载/导出入口。以保留正文和可核查的引用为准：当前官网实测 Word 会转换编号引用并附来源链接，优先下载 Word，需要纯文本时可另存 Markdown；实际菜单只有其他格式时据实选择。不要另写一份摘要冒充下载的报告。
- 下载到当前主题的 `2-报告原件/`。工具只能保存到下载目录时，依据本次下载返回的路径或下载记录定位文件，再复制到目标目录；不猜最近一个文件就是报告。同名文件已存在时用不同文件名或子目录，保留已有原件。
- 确认目标文件存在、非空、可读，检查正文主题对应这条方向，并核对来源部分是否保留，再登记「已下载」和实际路径。点击下载按钮、出现下载提示、只创建空目录都不算落盘成功。
- Markdown 中可能残留 `citeturn...` 之类内部标记；这些不是可点击的来源。不能只看有几条 URL 就认定引用完整。遇到此情况补存 Word 并检查正文编号与来源部分；原 Markdown 保留，不猜链接、不改写原件。其他格式同样要检查实际导出结果，不能把某次成功当成永久保证。
- 下载工具不支持或文件未落盘时，保留「待下载/受阻」，给出具体报告链接和目标目录，请用户只补这个步骤；其他可执行的任务继续。若下载的是 Word/PDF，收卷时从原件核对来源超链接，不能根据转写文字猜链接。

批量启动结束后，已下载的报告可以进入收卷，但不能因此漏掉后续巡检和下载。全部已核验下载后完成总对照；遇到确实无法继续的阻塞时，先整理已回来的并保留未完成项。汇报分别给出启动数、官网完成数和本地已核验下载数，不能把三种状态混成「全部完成」。

## 收卷

### 1. 登记

把 `2-报告原件/` 里的每份报告对上方向表的编号。看标题和正文判断，不靠文件名。对不上任何一条的单独列出来，问用户归哪条。只回来一部分时，先做回来的那几份，没回的在表里留空。

### 2. 转成文字

md 直接读。docx 和 pdf 转成文字放进 `3-报告转写/`，文件名用 `<编号>-<方向>.txt`：

```bash
textutil -convert txt "<原件.docx>" -output "3-报告转写/<编号>-<方向>.txt"
pdftotext -layout "<原件.pdf>" "3-报告转写/<编号>-<方向>.txt"
```

转出来是空的或乱码（多半是扫描版 PDF），告诉用户是哪一份，请他重新下载 Markdown 或 Word 版。

### 3. 摘要与对照

写 `4-摘要与对照.md`：

```markdown
## ① <方向>（<原件文件名>）
核心结论：三句以内
最有用的：3–5 条，每条一句，附报告里的来源链接

（每份一节）

## 对照
### 共识
### 矛盾
（谁说了什么，各自的依据）
### 只有一份提到的
```

只写报告里写了的内容。你自己的判断单独标成「我的看法」，用户要分得清哪些是报告说的、哪些是 AI 加的。

### 4. 问下一步

回复里写几行结论：最重要的三条共识、最值得注意的一个矛盾。附上文件链接，然后问用户下一步做哪个。可以说你推荐哪个，但在他回答之前不要动手：

1. 做成学习指南：交给 study-guide，在同一个主题文件夹里重新梳理主线、补前置知识、配图排版，做成能发到博客的知识页
2. 转成导图：交给 book-to-mindmap
3. 发到飞书：用 lark-cli，格式规则见全局 CLAUDE.md
4. 做成 skill：交给 skill-build
5. 补一轮 deep research：回到出题，编号接着排

最后更新 `0-说明.md` 的方向表和下一步。

## 文件夹

一个主题一个文件夹：工作区 `知识/调研/<主题>-<YYYY-MM-DD>/`，主题用中文短名。

```
0-说明.md          真问题、方向表、下一步
1-prompt.md        全部 prompt，和消息里给的一致
2-报告原件/        从官网下载的 md / docx / pdf 原件；也接收用户手动放入的报告
3-报告转写/        docx、pdf 转出的文字
4-摘要与对照.md
```

后续产出（学习指南、导图等）接着用 5-、6- 编号。

报告常常隔几天才回来，下个会话只读 `0-说明.md` 就要能接上，所以它固定这样写：

```markdown
# <主题>

真问题：<钢人轮后和用户确认过的一句话>
用途：<用户拿结果去做什么>
ChatGPT 项目：<项目名和链接；尚未创建时写未创建>
本批执行：<本次运行哪些编号；用户明确只要 prompt 时注明>
巡检间隔：<默认 60 秒，或用户指定值>
上一轮检查：<时间；尚未进入巡检时写未开始>
下一次检查：<时间；全部完成时写已结束>

| # | 方向 | 为什么单列 | ChatGPT 对话 | 状态 | 最后核验 / 说明 | 报告文件 |
|---|---|---|---|---|---|---|
| ① | <方向名> | <用户点名 / 补的理由> | <对话链接，未建则空> | 未启动 | <时间、追问或阻塞原因> | <2-报告原件/文件名，未核验落盘则空> |

下一步：<一句话>
```

## 红线

1. 摘要和对照里不编造报告没写的内容，也不编造来源链接。用户会拿它们做判断，编出来的东西看上去和真的一样。
2. 不删除、不改动 `2-报告原件/` 里已有的文件。那是官网报告原件，可能没有第二份；重跑或重下时另存。
3. prompt 的背景里不写账号、密钥，不写未公开的他人信息。prompt 会被发到外部服务。
