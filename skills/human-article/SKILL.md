# 活人感写作

## 定位

- **默认把文章写成一篇值得读完的中文长帖。**读者应当感觉对面有一个具体的人。这个人知道一些事，也有不知道的地方。他愿意讲细节，敢下判断，偶尔岔开一句，随后还能把话接回来。
- **写一篇值得读完的中文长帖，让读者感觉对面是个具体的人。** 活人感先靠扎实的材料，再靠作者说话的位置，最后才是语气。句子顺着中文互联网长回答和长帖的自然韵律走，避免空泛的机构腔、喊口号式演说腔、营销腔和模型腔，也不靠口头禅、粗口、错别字和网络梗硬凑。
- **把读者能得到什么放在前面，主线清晰、段落通顺最要紧。** 这个 skill 只写产品宣传和知识介绍两种公众号文章，见 `references/体裁.md`。说话的人是作者本人，一个二三十岁的 AI 行业独立开发者。读者多半关注 AI、常刷 AI 资讯，不一定写代码，认识 Claude Code、Cursor、ChatGPT、DeepSeek 这些主流产品，也熟悉 skill、prompt、Agent 这些说法。文章主体是读者想知道的事，作者像跟朋友聊天一样把事讲清楚、讲出吸引力，让人从头读到尾停不下来。作者只在他做过的、看到的、判断的地方说一两句，感受轻轻带一句。构思排第一，活人感排第二，两件事顾不全时先保住主线。
- **全流程由你独立操盘，只在第四步停下来问作者。** 先想清楚要传递什么信息、全局怎么构造，把文章框架、叙事主线、起承转合、段落衔接、吸引读者的点和具体表述想顺了，这是整个流程里最要紧的一步，构思好全局才能保住文章的吸引力，想好以后再带着问题找资料。讲什么、按什么顺序讲由你定，作者的表达诉求、写作要求和希望呈现的内容只作参考，不必全文照搬。他列的一定要放的东西必须写进文章，在主线里落实，分几块、先后怎么排按主线定，不直接当成提纲。规则到要用的那一步再读。作者的说话位置和构思想在心里，不写成文件。材料笔记、初稿、改稿写成工作目录里的文件，下一步从文件接着做。遗漏或不明白的信息攒到第四步一次问清。

## 红线

- **产品带来的结果、数字、有名有姓的人和别人的反应不编造。** 作者做过的具体事情以材料为准，项目记录里他自己做的、他让 AI 去做的，都算他做的，可以写「我」。打比方、普通人都有的生活场景（可以写成作者的经历）、模拟一次使用、感受和洞见，可以照 `references/现实与边界.md` 替他写，全部列进 `替你写的.md`，他会自己审。
- **截图和录屏里没公开过的个人信息先裁掉。** 画面里有邮箱、手机号、私信、真人照片的，先裁掉或者换一帧，换不了就不用。
- **不替作者发布。** 文章写好交给他，发不发、发在哪里由他定。

## 规则冲突时的先后

- **红线在任何时候都要守住。** 红线不参与排序，事实准确归红线管，不拿来和别的规则比。
- **规则顶住时，先保主线清晰和段落通顺，再保读者得到什么和活人感。** 写作时几件事顾不全，按主线清晰与段落通顺、读者要知道的事、作者在不在场、读着的节奏、文采这个先后顺序取舍。哪条规则会让第三步定下的主线断开、段落接不上（见 `references/写作.md` 的「段和段怎么往下走」），就先保住主线和通顺。读者得到什么和活人感，按「定位」和 `references/写作.md` 的「读者在前，作者带路」「判断和感受」来写。
- **其余规则按离这一篇从近到远的顺序排。** 排在主线和活人感后面的，依次是作者明确要求的文体、语气、交付形式和他说不写的东西，接着是 `references/现实与边界.md`，再往后是 `references/体裁.md` 里这一篇那一节（它比 `写作.md`、`改稿.md` 其余的写法具体，离这一篇更近，和主线、活人感顶住时仍按主线和活人感），最后是 `references/写作.md` 和 `references/改稿.md` 里其余的写法。
- **检查脚本只执行写明的硬禁令。** 警告项只是提醒，不能替作者决定文体。
- **作者在对话里关于怎么回复他的要求，只管你和他对话，不用在文章上。**

## 在哪里写

- **一篇文章用一个新会话写。** 当前会话已经读过别的文章、讨论过很多版稿子的，先建议作者开新会话，避免写作时不自觉模仿那些文字。
- **每篇建一个工作目录，只在这个目录里写文件。** 默认放在环境变量 `HUMAN_ARTICLE_OUT_DIR` 下的 `<日期_主题>/`，没设就是 `~/claudecode_workspace/内容/自媒体/微信文章/2_产出/<日期_主题>/`，作者指定了别处就用他说的。写完会有 `材料笔记.md`、`新图/`、`图/`、`图片说明.md`、`1-初稿.md`、`替你写的.md`、`2-改稿.md`、`文章.md`、`交稿说明.md`，做了第八步还有 `发给Gemini的全文.md`、`3-gemini改稿.md`、`gemini改动说明.md`、`文章-gemini.md`。
- **路径全部用绝对路径。** `skill 目录` 就是这份文件所在的目录，命令里的 `<skill 目录>`、`<写作档案>`、`<工作目录>` 都换成绝对路径。
- **去写作档案里取公众号固定的开头结尾和二维码。** 写作档案取环境变量 `HUMAN_ARTICLE_PROFILE_DIR`，没设就是 `~/claudecode_workspace/内容/自媒体/写作档案/`。`公众号固定开头结尾.md` 写正文第一句和结尾那几行，`素材/公众号二维码.jpg` 在生成成稿时用。找不到就问他放在哪里，写作档案里的其他文件先不读。
- **按步骤调用 `scripts/` 里的六个脚本。** `embed_images.py` 生成成稿，`make_gif.sh` 把录屏转成动图，`check_prose.py` 在改稿时查禁用项，`check_repeats.py` 在改稿时查作者以前改过不止一次的说法，`gemini_revise.py` 和 `compare_revision.py` 在第八步交给 Gemini 改稿、对照两版时用。

## 一、确定写哪一种

- **想清楚写给谁、读完要他怎么样。** 读作者的请求，对着 `references/体裁.md` 开头那两条，挑这一篇是产品宣传还是知识介绍，兼有的两节都读。这一步只挑，第三步再细读。
- **建好工作目录，在 `材料笔记.md` 开头写下读者会问的问题。** 工作目录的位置见「在哪里写」。在 `材料笔记.md` 开头记下这篇大概写什么、读者读它会问哪几个问题、为了回答这些问题要去哪里找什么，三五行就够。
- **方向说不清的留到第四步问。** 只有连写的是哪一件东西都看不出来，才先问一句。请求里没给项目位置，先在工作区根目录的 `README.md` 里找。

## 二、找到材料

- **按 `材料笔记.md` 开头的问题找事实材料。** 读项目、看线上、看现成的图、看作者对外发过的东西，做法见 `references/材料.md`。
- **这一步不定主线、不排轻重。** 材料里的先后、分组和说法不决定文章怎么写。
- **边找边在 `材料笔记.md` 里接着记。** 记下不能写的、拿不准的、要问作者的。

## 三、构思文章框架

- **先读 `references/体裁.md` 里这一篇那一节和它点名的范文。** 读完在心里想清楚下面几件事，不写成文件，每一段具体写什么留到写的时候再定。
- **想清楚读者读完能得到什么，拿这句话当主线。** 站在读者的角度想，他通过文章知道了什么、能去做什么、省掉了什么麻烦。说不出来就回去看材料和作者的话，想清楚读者为什么要点开这一篇。
- **顺着读者会按什么顺序问往下排。** 顺着读者心里冒出来的下一个问题往下排，一个问题一块。讲了它是什么，他会问跟我有什么关系。讲了能做什么，他会问怎么用、靠不靠谱。讲了好处，他会问要花什么。`体裁.md` 里有这类文章常见的顺序。长文分三四块，每块一个小标题，让小标题和加粗连起来读，就能知道文章讲了什么。
- **想好开头怎么进来。** 开头可以有铺垫或直入主题，都要和主线相关。先放读者最想要的那个结果，或者他正碰上的那个麻烦，再说这是什么。
- **想好每一块讲透哪一两件事。** 同时在心里定下作者在哪里出来说一两句，哪几处要配图。

## 四、确定信息

- **检查信息有没有缺失，所有要问的在这一步一次问完。** 做法见 `references/材料.md`「问作者」。重点核对三件事，一是不确定的项目信息，二是这篇表达的重点和作者现在最想说的判断，三是作者的感受，也就是他和这件事实际发生过什么，哪个瞬间、数字、动作或原话最让他在意。不要先交一篇空稿，再期待作者往里补活人感。问完按他的回答把构思想定，再动笔。
- **作者希望你自主决策时，跳过提问直接写。** 如果作者说「先写一版」「不要问我，先按推荐来」，就照 `references/现实与边界.md`「能替作者写的」去补，补的每一句都列进 `替你写的.md`。材料真不够、又不能问的时候，宁可交一篇更短、更实的文章，也不碰红线把结果、数字、真人和别人的反应硬安到作者身上。

## 五、写作

- **动笔前只读正面的写法，先不读改稿规则。** 依次读 `references/写作.md`、`references/现实与边界.md`，把 `体裁.md` 那一节再翻一遍，再读写作档案的 `公众号固定开头结尾.md`。
- **先按构思配齐材料和图。** 每一块缺事实的，回原文和线上再查。要的图现成没有，照 `references/配图.md` 去截、录，或者写代码画出来。图放进 `图/`，文件名写成 `图N-主题.扩展名`，编号按在文章里出现的先后排，并在 `图片说明.md` 里每张补一行，写清编号、文件名、截图还是动图、哪天的、和现在的产品哪里不一样、哪里打过码。
- **从读者会碰上的那件事写起，边讲事情边处理他下一步的疑问。** 像给一个感兴趣但不了解此事的人解释，把读者想知道的事放在前面，讲它怎么帮上忙（见 `写作.md` 的「读者在前，作者带路」「判断和感受」）。开头尽快写到具体的事情，不预告全文结构。分类从材料里来，除非用户明确要清单或教程，不先把题目命名成几个成本、几层原因、几个阶段。
- **一段先完成眼下这一件事，新段落必须增加一件新东西。** 后一段接住前一段留下的问题，推进靠材料和因果，不靠「更深一层」「真正的问题」这类路标。写到事情已经讲完就停，不在末段重新摘要全文，不强装升华、首尾呼应或时代意义。
- **白话打底，把话说全、不省字，不追求信息密度。** 主语和动作先出来，让读者尽早知道谁做了什么，再往后接时间、原因、条件和例子。动作、细节或原话已经把感情写出来就停一下，不追在后面替读者解释。
- **把正文写进 `1-初稿.md`，再把替他写的句子列进 `替你写的.md`。** `1-初稿.md` 里只放文章本身，格式按 `写作.md`「公众号的格式」。`替你写的.md` 分成「生活场景和打比方」「模拟的使用和普通人的流程」「感受和洞见」三组，每条写原句和第几段，一处都没有就写「没有」。

## 六、审稿

- **按改稿规则逐遍审改。** 初稿写完再读 `references/改稿.md`，按 `改稿.md` 的几遍从头读到尾，看到问题当场改。先保住已经写活、读者一读就懂的地方，再拆读着像 AI 的地方。
- **清零成稿绝对不能出现的东西。** 翻案腔、三项以上的同构排比、给抽象名词配具体动词的抒情、动词名词化、破折号、提示性冒号、「说白了」这类话、洞察路标、商业黑话和模型黑话、包装抽象概念的借喻，命中一项就不能交稿。这里禁绝整类修辞动作，换一套字面做同一个动作同样算违规，清单和改法见 `改稿.md`「第五遍」。跑一遍 `scripts/check_prose.py`，失败就接着改，直到禁用项清零。
- **保存改稿并更新清单。** 改好的全文写进 `2-改稿.md`，`替你写的.md` 跟着改，改完就交，避免多轮修改把写活的地方改坏。
- **生成成稿。** 跑下面这一行，脚本会把 `[图N]`、`[视频N]` 换成 `图/` 里的文件，把 `[公众号二维码]` 换成二维码，没找到的图会列出来。

```bash
python3 <skill 目录>/scripts/embed_images.py <工作目录>/2-改稿.md <工作目录>/图 <工作目录>/文章.md <写作档案>/素材/公众号二维码.jpg
```

## 七、交稿

- **先核对一遍图。** 看脚本有没有报没找到的图，再打开 `文章.md` 从头看一遍，确认图都在、位置都对。
- **知识介绍附来源。** 全靠公开材料写成的，文末列出对结论重要的少数来源，产品宣传不附。作者另有要求时听他的。
- **只交作品，过程写进交稿说明。** `文章.md` 里只放文章。另写一份 `交稿说明.md` 放进工作目录，并贴在对话里，按下面顺序写清楚。
  1. 第一行写这篇是写给谁的。
  2. `文章.md` 的链接，提醒他在编辑器里预览才看得到图。
  3. 一句话说读者读完能得到什么，长文列出小标题，再说开头怎么把读者带进来。
  4. `替你写的.md` 里的句子，请他看像不像他会说的。
  5. 按默认处理的小事各怎么处理的，以及要问他却没问到的事。
  6. 标题他没给的，附两三个候选。
  7. 发之前要他做的事。
- **后续改动都经过改稿这一步。** 他要改哪里，先说给你，你在稿子里改，再生成成稿，让规则的毛病看得见。他要拿去直接发，就按他的意思改。
- **把作者读完说的话按去处归档。** 他补充对这件事的看法、关于他自己的新说法和只管这一篇的要求，留在对话里照着改。他说哪里写得不对，把原话记进反馈账本 `0-反馈账本.md`，再读 `0-改规则时读.md` 去改规则。这两个文件在环境变量 `HUMAN_ARTICLE_FEEDBACK_DIR` 指的目录，没设就是 `~/claudecode_workspace/工具/去AI味说人话写作/1-工作区/01-skill本体/`；目录不存在，就把原话记进工作目录的 `反馈.md`。他发出去以后给了终稿或链接，存进工作目录，和 `文章.md` 对一遍。

## 八、交给 Gemini 再改一遍（作者要的时候才做）

默认不做，作者说「用 Gemini 改一下」「让 Gemini 再过一遍」时才做，交稿以后才提也一样。Gemini 改稿的长处是把省掉的字说全、读着更顺，短处是会删图、添原文没有的说法、把「我」删过头，它改完要核对一遍再交。

- **调脚本交给 Gemini。** 拿图还是 `[图N]` 占位的 `2-改稿.md` 跑下面这行命令。脚本读 `references/gemini改稿.md` 里的 prompt，把文章接在后面调 Gemini API，正文写进 `3-gemini改稿.md`，Gemini 附的说明写进 `gemini改动说明.md`。API 的 key 取环境变量 `GEMINI_API_KEY`，没有就读 `~/.config/gemini/api_key`；走本机代理，地址取 `GEMINI_PROXY`，默认 `http://127.0.0.1:7897`。默认模型 `gemini-4-argon`、思考强度 `high`，可用 `--model`、`--thinking` 切换，服务忙一共试三次。接口不通、额度用完，或者作者说要用网页版时，脚本会写一份带 prompt 加文章的 `给Gemini网页.md`（加 `--web` 就只写这一份），请作者贴进 Gemini 网页，把结果贴回来存成 `3-gemini改稿.md`。

```bash
python3 <skill 目录>/scripts/gemini_revise.py <工作目录>/2-改稿.md <工作目录>/3-gemini改稿.md
```

- **对照两版差异。** 跑 `python3 <skill 目录>/scripts/compare_revision.py <工作目录>/2-改稿.md <工作目录>/3-gemini改稿.md`。脚本会列出少了的图和固定的行，新出现的数字、名字、括号里的话和程度词，两版的字数、一句一段的比例、每千字的「我」和「你」，再跑 `check_prose`。脚本负责检查字面差异，像把「看了一眼后台」写成「把后台每条记录都核对了一遍」这种把作者做过的事说满的地方，由你逐段读出来。
